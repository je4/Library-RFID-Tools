## 1. Architecture & Envelope Hierarchy

All messages sent and received by `rfid-headless` over WSBroker follow a two-tier envelope hierarchy:

1. **Outer Transport Envelope (`Event<T>`)**: Defines routing, messaging metadata, correlation IDs, timestamps, and log summaries.
2. **Inner Generic Payload Envelope (`RfidPayload<T>`)**: Encapsulates the specific RFID event name (`event`) and strongly-typed data record (`data`).

```
+-----------------------------------------------------------------------------------+
| Event<RfidPayload<T>>                                                             |
|   id: "uuid-or-snowflake"                                                         |
|   refId: "request-id-to-correlate"                                                |
|   channel: "all" / "intern"                                                       |
|   source: "rfid-station-01"                                                       |
|   target: "dashboard-ui" / "all"                                                  |
|   type: "message"                                                                 |
|   message: "[TAG READ] Reader: gate-01 | UID: E004... | ItemID: 3012..."         |
|                                                                                   |
|   +-----------------------------------------------------------------------------+ |
|   | data: RfidPayload<T>                                                        | |
|   |   event: "rfid:tag_read"                                                    | |
|   |                                                                             | |
|   |   +-----------------------------------------------------------------------+ | |
|   |   | data: TagReadData / TagsClearedData / WriteTagResponseData / ...      | | |
|   |   |   uid: "E004010000001234"                                             | | |
|   |   |   itemId: "3012345678"                                                | | |
|   |   |   readerId: "gate-01"                                                 | | |
|   |   |   ...                                                                 | | |
|   |   +-----------------------------------------------------------------------+ | |
|   +-----------------------------------------------------------------------------+ |
+-----------------------------------------------------------------------------------+
```

## 2. Event Envelope (`Event<T>`)

Defined in package `org.objectspace.wsbrokerclient.event`.

### Fields

| Field | JSON Property | Java Type | Description |
| :--- | :--- | :--- | :--- |
| `id` | `id` | `String` | Unique message identifier generated by sender or broker. |
| `refId` | `refId` | `String` | Correlated message identifier (matches `id` of originating request). |
| `channel` | `channel` | `String` | Target broadcast channel name (e.g. `all`, `intern`, `gates`). |
| `time` | `time` | `Instant` / `String` | ISO-8601 UTC timestamp of message generation. |
| `source` | `source` | `String` | Client name of the sender (e.g. `rfid-station-01`, `web-ui`). |
| `target` | `target` | `String` | Intended recipient client name or channel. |
| `type` | `type` | `EventType` / `String` | Event category (`message`, `action`, `ping`, `pong`, etc.). |
| `session` | `session` | `String` | Logical scanner session identifier. |
| `message` | `message` | `String` | Human-readable log / summary text. |
| `error` | `error` | `String` | Error description if the event represents an error. |
| `data` | `data` | `T` | Generic payload object (typically `RfidPayload<T>`). |

## 3. Generic RFID Payload Envelope (`RfidPayload<T>`)

Defined in package `org.objectspace.rfid.headless.payload.RfidPayload`.

```java
public record RfidPayload<T>(
    @JsonProperty("event") String event,
    @JsonProperty("data") T data
)
```

### Fields

| Field | JSON Property | Type | Description |
| :--- | :--- | :--- | :--- |
| `event` | `event` | `String` | Name of the event or command response (e.g. `rfid:tag_read`, `rfid:tags_cleared`, `rfid:device_metadata_response`, `rfid:write_tag_response`, `rfid:write_afi_response`). |
| `data` | `data` | `T` | Strongly-typed payload data record. |

---

## 4. Outbound & Inbound Event Types

| Event Name | Direction | Payload Type | Description |
| :--- | :--- | :--- | :--- |
| `rfid:tag_read` | Outbound | `TagReadData` | Broadcast when an RFID tag is scanned and decoded. |
| `rfid:tags_cleared` | Outbound | `TagsClearedData` | Broadcast when RF field becomes empty, reader disconnects, or after write operations. |
| `rfid:get_device_metadata` | Inbound | `JsonNode` / `Map` | Query reader hardware device ID, type, and diagnostics report. |
| `rfid:device_metadata_response` | Outbound | `DeviceMetadataData` | Response containing hardware diagnostics and device info. |
| `rfid:write_tag` | Inbound | `JsonNode` / `Map` | Command to write ISO 28560 metadata and AFI to transponders. |
| `rfid:write_tag_response` | Outbound | `WriteTagResponseData` | Response reporting success, failures, and per-UID error details. |
| `rfid:write_afi` | Inbound | `JsonNode` / `Map` | Command to write AFI security byte to transponders. |
| `rfid:write_afi_response` | Outbound | `WriteAfiResponseData` | Response reporting AFI write status per transponder UID. |

## 6. Inbound Commands & Routing

### 6.1 Flexible Payload Parsing

The parser (`WsBrokerPayloadParser`) accepts multiple command representations to guarantee maximum compatibility with web, Go, Python, and legacy clients:

1. **Direct root attributes**:
   ```json
   { "event": "rfid:write_tag", "uid": "E004...", "itemId": "123", "afi": "07" }
   ```
2. **Nested `data` structure**:
   ```json
   { "data": { "event": "rfid:write_tag", "data": { "uid": "E004...", "itemId": "123" } } }
   ```
3. **Array batch format**:
   ```json
   { "event": "rfid:write_tag", "tags": [ { "uid": "E004...1", "itemId": "A" }, { "uid": "E004...2", "itemId": "B" } ] }
   ```
4. **Map format**:
   ```json
   { "event": "rfid:write_tag", "tags": { "E004...1": { "itemId": "A", "afi": "07" }, "E004...2": { "itemId": "B", "afi": "C2" } } }
   ```

### 6.2 Multi-Reader Targeting & Read-Only Enforcement

- **Addressing**: Commands containing `reader_id` or `readerId` are routed to the specific `HeadlessReaderInstance`. If omitted, the command defaults to the active reader or broadcasts across instances.
- **Read-Only**: Any reader instance with `<readonly>true</readonly>` will immediately reject `rfid:write_tag` and `rfid:write_afi` commands without accessing reader hardware.

### 6.3 Request-Response Correlation (`refId` & `id`)

When an incoming command specifies an `id`, the corresponding response will set `refId` to that `id`. This allows clients to reliably correlate responses in asynchronous multi-client environments.
